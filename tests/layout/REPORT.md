# Pad 铺满适配与扫码回填验收

测试日期：2026-11-01。HTTPS／直接摄像头版本在改动前已提交为 `906d907`。

## 布局修复

以 1920×1080 为控件尺寸基准，使用实际可见视口统一缩放字体、图标、按钮、图片与弹窗。
画布宽高随浏览器可用空间扩展，左右面板使用剩余空间，不再固定 16:9 居中留白。
通过 visualViewport 高度兼容动态浏览器工具栏，安全区域仍由 env(safe-area-inset-*) 处理。
修复主页 scoped 的 100vh 在路由懒加载后覆盖画布高度的问题；测试入口也改用懒加载，覆盖此回归。

实测 15 种 CSS 视口尺寸：800×600、1024×768、1280×800、1366×912、1536×865、1536×890、
1536×960、1536×1080、1920×1200、600×960、768×1024、800×1280、1536×680、1024×480、2560×1600。
其中 1536×890 模拟用户截图扣除平板浏览器栏后的内容区域；适配不依赖屏幕毫米尺寸。

主界面、登录、车头拍照、货物拍照、行驶证、证件摄像头、通行码、历史记录、预约、用户管理、
车牌修改和农产品选择，共 **12×15＝180 组检查、2850 个控件位置，全部通过**。

`audit.js` 验证画布铺满可用视口、横纵缩放比例一致、懒加载后的主页填满画布、
控件不越界或被容器裁切、主界面无需滚动才能操作。历史表格／照片列表超过一页时仍可分页／滚动。

## 样例二维码与操作测试

浏览器测试运行实际生产扫码、解析、上传和 Dashboard 回填代码；相机帧由用户提供的样例 PNG 合成。
API 隔离在 127.0.0.1:5186，网络摄像头模拟离线，不连接现场设备。
扫码上传的 multipart JSON 由测试服务解析并验证通行码；历史数据使用明确的模拟记录。

- 样例二维码识别车牌“豫A9237L”、颜色代码 1、入口重量 16800、出口重量 **16440 kg**。
- 初版验证单击“通行码”直接进入相机；最新交互改为先选“摄像头”或“扫码仪”，见下方复测。
- 强制移除 BarcodeDetector，验证 ZXing 兼容路径；原图以及旋转 0°、30°、90°、180°、270° 的 240 像素样例均识别成功。
- 初版手动截帧已验证；最新改为“照片识别”，通过系统照片选择器读取已有图片，见下方复测。
- 无 WebSocket 推送时，车牌、颜色和称重立即回填；模拟历史补齐电话、挂车、车型、货箱、尺寸和查验次数。
- 预先手输手机号，扫码后原值保留，历史只补空字段。
- 首次上传模拟失败，识别结果仍保留在主界面，点击“重试上传”后成功。
- 7 个 Node 协议测试覆盖 14 段映射、金额／重量单位、扩展字段、坏码、空值、颜色后缀及金额展示换算。
- 使用真实 Flask mobile.py Blueprint 在独立测试客户端中校验 multipart 上传、UTF-8 文件存储；
  单独执行真实后端 _parse_passcode 函数验证样例字段一致。未启动生产应用、目录监听或硬件服务。

## PC 对照与提交确认页

对照 PC 端 Dashboard 的 mobile_passcode、buildSubmitPreview 和提交逻辑，以及 DetailDialog 的通行码字段。
主页显示车牌、颜色和出口称重；完整通行码数据进入提交确认页和提交请求。
站点编号通过字典接口显示成站点名称；二维码图片在 Pad 本地生成，无需等待 WebSocket。

使用样例完成“相机扫码 → 本地回填 → 选择货物 → 打开提交确认页”，逐项读取页面字段：

完整交易流水号与通行 ID、出口时间 2026-11-01T10:43:22、车辆状态默认值均一致。
入口与出口站字典使用测试站名，电话、车型等历史补齐使用模拟数据，货物白菜由测试手动选择。
支付方式原始代码 0 保留，按 PC 字典显示“未知”，提示信息可查看原始代码。
二维码中的 fee / payFee 原值均为 125100 分，页面分别显示总交易金额／应收金额 1251.00 元，提交保留原始值。
保留数值 0，避免支付方式、介质或车辆状态因真假值判断而变为空。

确认页在 1536×890 视口检查 73 个控件，无越界／裁切；本地生成的 300×300 二维码再次经 ZXing 解码，

- 主页先弹出“摄像头／扫码仪”选择，仅选择摄像头后才请求镜头。
